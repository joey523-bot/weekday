# REM-002 稍后提醒

## 行为

详情中展开“稍后提醒”后，可选择10/30/60分钟后、自选日期时间或每小时循环。只在用户点击保存/开启时写入；不改变原事项日期及原始提醒设置。循环第一次为1小时后，截止时刻不包含在发送区间内；默认截止北京时间当天22点，22点后不预填，须明确选择未来截止时间。若剩余时间不足1小时，要求延后截止时间或改选单次。

首页及事项列表按事项日期＋时刻标记到点未完成，不以系统通知是否成功送达判断到期。每分钟更新可见列表；不改变用户已选择的筛选。

时间口径固定Asia/Shanghai。现有项目没有独立免打扰时段设置，本次遵守用户指定的循环起止范围；单次时间由用户明确选择。未增加锁屏原生动作，不承诺绕过静音/专注模式。

## 存储与调度

- `reminder_snoozes`按账号/事项保存独立计划，token区分重设版本，next_at为首触发锚点；下次时刻按每小时间隔派生，不回写或污染账号快照。
- `reminder_snooze_deliveries`按token＋设备＋轮次原子占位。重复/并发Cron每设备每轮最多尝试一次，明确HTTP拒绝可重试；网络结果未知保留占位，优先防重复，可能漏发。
- 每5分钟Cron扫描，分钟级计划到点后才发送，通常在下一轮检查；调度/网络故障时不能保证时延。循环漏过多轮只取最近一轮，不密集补发。单次全部设备尝试结束后停用，不因后来添加设备而重发旧提醒。
- 保存计划、占位和发送前均校验账号归属、最新未完成事项及有效订阅。账号快照完成/删除与停用计划在同一数据库事务中；恢复事项不会自动重启旧循环。编辑日期保留原编辑语义，独立稍后计划不暗中调整。
- 用户停止或截止后不再启动新的发送。已交给推送服务的在途通知无法撤回，TTL最长5分钟，循环以剩余截止秒数进一步收紧。
- 原事项规则同步由删除重建改为保留last_sent_key的upsert，避免同步后重发已发送的旧通知。
- 本机通知/天气状态不再误标成账号待同步内容；共享快照真实变化仍进行版本冲突保护。

## 本地验证与发布顺序

```sh
npm ci --prefix workers/salary-notifier
node --test tests/*.test.mjs
# 浏览器测试依赖Playwright及Chrome，全部接口使用fixtures，不发真实通知
WEEKDAY_PLAYWRIGHT_PATH=/path/to/playwright WEEKDAY_BROWSER_EXECUTABLE=/path/to/chrome node tests/snooze-browser.mjs
```

发布前必须核对当时正式基线并保留已发布分类功能，重新验证受影响交集。获得发布授权后，先执行追加迁移`cloudflare/migrations/0005-reminder-snoozes.sql`，再发布Pages与Worker；否则新版账号同步会因缺表失败。迁移无数据改写、不自动创建循环；可重复执行。发布失败时回滚Pages/Worker到发布前版本并保留新表，不删除业务数据。若回滚后用户继续完成事项，应在再次启用REM-002前核对并停用已完成/删除事项的残留计划。

真机稍后通知送达、跨设备完成/停止、系统静音表现须发布后验收；本地SQLite/Chrome和构建不替代生产D1或iPhone验收。
